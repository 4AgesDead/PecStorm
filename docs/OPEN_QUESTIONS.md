# Открытые вопросы организаторам

Статус на 3 ноября 2026: **ответы не получены** (ни по одному пункту).
Ниже — что именно заблокировано каждым вопросом и какое допущение сейчас
используется в коде. Ни одно из допущений не подтверждено организаторами;
формулировки в отчётах должны это сохранять.

| № | Вопрос | Что заблокировано / текущее допущение |
|---|---|---|
| 1 | Где 3D-модель грузовика (слайд 9), в каком формате? | Монокулярный 3D (`monocular_pnp`) невозможен: нет модели/размеров. На кадрах с одним видом оценка 3D не выдаётся как измерение (только прогноз). |
| 2 | Какую точку возвращать: actor pivot `SM_AA_track`, центр кузова, центр масс, центр bbox? | Оценки сравниваются с `pivot`. Детектор даёт центр bbox → систематический сдвиг. Введён постоянный `FusionConfig.anchor_offset_m`, оценённый на train-кадрах; это приближение, а не решение. |
| 3 | В каких единицах и мировой системе `Loc_X/Y/Z`? | Принято: сантиметры Unreal, `X_u=X_ue, Y_u=-Y_ue, Z_u=Z_ue`. Проверка — согласованность проекции GT-пивота с кадром (`experiments/projection_sanity.py`), но она не доказывает систему координат однозначно. |
| 4 | Какая система осей/rotation order у camera transforms? Можно ли получить готовые матрицы? | Используется формула FRotator UE4 + эмпирическая поправка знака pitch. Без подтверждения возможна зеркальность/сдвиг осей, которые маскируются сдвигом якоря. |
| 5 | Достаточно ли sensor 23.76×13.365 мм и focal 20 мм для intrinsics? Каковы principal point, distortion, filmback, crop/overscan? | Принято: pinhole, PP в центре кадра, дисторсия 0, сенсор используется целиком. Любой crop/overscan смещает `fx/fy` и `cx/cy`; это прямо влияет на глубину. |
| 6 | Гарантирована ли синхронность потоков, общий frame 0, есть ли PTS/time offsets? | OpenCV PTS не отдаёт; синхронизация по `frame / fps`. Сдвиг 50 мс на скорости ~2.5 м/с даёт ~0.12 м ошибки (оценка в `experiments/robustness_benchmark.py`, синтетика). |
| 7 | Нужна ли оценка на каждом кадре 30 Гц, реже или только на заданных timestamp? | Сейчас оценки выдаются на всех кадрах общей области 0..1000, в том числе `PREDICTED_ONLY`. Формат не согласован. |
| 8 | Нужны ли 3D-координаты на однокамерных сегментах? Предполагается ли 3D-модель? | Без модели монокулярная метрическая глубина не определена. Сейчас такие кадры помечаются `MONOCULAR`/`PREDICTED_ONLY`, измерение не выдаётся. |
| 9 | Точный формат вывода: CSV-колонки, разделитель, единицы, семантика frame/time, точность? | Использован DTO §11 брифа (`out/truck/estimates.csv`, запятая, метры, `frame_id` = номер кадра). Может не совпасть с формой сдачи. |
| 10 | Как оценивается качество (MAE/RMSE/порог/доля кадров/трекинг) и какой допуск проходной? | Считаются MAE/RMSE/median/P95/P99/max по `MEASURED` + покрытие отдельно. Численного target нет, поэтому «проходной» результат не определён. |
| 11 | На проверочном наборе тот же грузовик/камеры/маршрут или новые объекты/сцены? | Влияет на переносимость `anchor_offset_m` и порогов. Сейчас сдвиг калибруется на train-кадрах и на hidden не подбирается. |
| 12 | Ограничения на GPU/CPU, Python, размер модели, время выполнения? | Прогон на CPU: `yolov8x` при `imgsz=960` ≈ 0.5–0.6 с на кадр камеры. Полный набор — десятки минут; при жёстком лимите времени нужен меньший `imgsz`/модель. |
| 13 | Разрешены ли pretrained open-source weights, fine-tuning, внешние библиотеки, интернет? | Используются `ultralytics` (YOLOv8, лицензия AGPL-3.0) и COCO-веса; fine-tuning не делался. Лицензионные ограничения для сдачи не подтверждены. |
| 14 | Можно ли использовать GT только на train; как устроен hidden test? | GT используется для (а) оценки и (б) калибровки постоянного сдвига якоря на train-кадрах 0..500; проверка — на 600..1000. Если GT на hidden недоступен, пайплайн работает без него. |
| 15 | Можно ли получить исходный GT-CSV без Excel-порчи двух ячеек? | Кадры 402 (`Loc_X`) и 691 (`Loc_Y`) исключены из оценки; sidecar-гипотеза `8.13`/`7.25` не применяется (`verified_by_organizer=false`). Потеря — 2 кадра из 1002. |
