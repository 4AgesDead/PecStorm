# Защита проекта «Пеленга»: вопросы и ответы

> Короткие ответы для защиты. Все числа — из артефактов репозитория
> (`docs/RESULTS.md`, `results/`, `out/truck/`), проверены 04.11.2026.
> Если ответа нет — так и говорить: «не подтверждено / вопросами занимались».
> Вопросы без ответов для тренировки — `docs/DEFENSE_QUESTIONS.md`.

## 0. Карточка проекта за 30 секунд

**Что сделано:** полный конвейер «5 камер → детекция → 3D-триангуляция →
трекинг Калмана → оценка против GT → веб-пульт и видео».

**Финальная конфигурация:** ансамбль `v1 (yolov8s) + v2 (yolov8m) +
v4b (fine-tune)` + якоря по наборам видов + азимутальный якорь.

**Главные числа:** MAE **1.98 м**, медиана **1.42 м**, покрытие **82.3 %**,
holdout 700..1000 — **1.98 м / 67.4 %**, recall-прокси **0.676**,
precision-прокси **0.790**.

**Потолок:** с оракульными боксами (GT + 3D-модель) — **95.5 % / 1.29 м**.

**Реальное время:** веб-пульт на одной **v4b** — **8.5–9.5 fps** на 5 камер,
живой прогон: **81.7 % / 2.89 м** (медиана fps 8.53).

**Тесты:** 90, все зелёные. Единая команда: `pecstorm`.

---

## 1. Задача и данные

**Q: В чём задача?**
A: По синхронным видео с нескольких калиброванных камер определять 3D-координаты
движущегося объекта и восстанавливать траекторию во времени. В наборе «Пеленга»
5 камер, один грузовик, 1001 кадр.

**Q: Что дано?**
A: 5 MP4 1920×1080, 30 fps, кадры 0..1000; CSV с позами камер; GT-траектория
пивота; GT содержит битые ячейки в кадрах **402 и 691** — они исключены.

**Q: Почему cam1/cam2 видны не всё время?**
A: В датасете cam1 и cam2 дают детекции только в кадрах **0..500**, cam4 — в
основном после 600. Это ограничивает покрытие в конце клипа, а не «баг
конвейера».

**Q: Что такое пивот?**
A: Точка актора из GT (не центр bbox). Центр бокса и пивот — разные физические
точки; их расхождение — главная причина систематической ошибки и якорей.

**Q: Есть ли 2D-разметка?**
A: Нет. Поэтому обычные precision/recall не измерить; используются
**прокси-метрики**: «пивот попал в bbox» и точность боксов относительно GT.

**Q: Почему нельзя просто обучить end-to-end 3D?**
A: Можно пробовать, но нет большой 3D-разметки, а масштаб/единицы мира
не подтверждены. Конвейер с явной геометрией интерпретируем и проверяем по
частям; end-to-end — направление развития.

## 2. Архитектура

**Q: Из каких стадий состоит конвейер?**
A:
1. детекция YOLO на каждой камере;
2. сопоставление видов (`single_target` — один объект);
3. триангуляция + LM-уточнение, порог невязки 50 px;
4. трекинг Калмана (CV-модель), гейт Махаланобиса 10σ;
5. якоря: 3D-сдвиг по набору видов + азимутальная поправка;
6. оценка MAE/покрытия против GT;
7. визуализация: видео, графики, веб-пульт.

**Q: Почему `single_target`, а не эпиполярные пары?**
A: В кадре один грузовик; `single_target` берёт лучшую детекцию каждой камеры и
устойчивее к несогласованным 2D-сдвигам. Для нескольких целей нужен другой
режим и пересмотр гейта.

**Q: Сколько видов нужно для 3D?**
A: Минимум 2 (`min_views=2`). При одном виде 3D-точка не восстанавливается;
монокулярный режим не используется.

**Q: Как выбирается порог триангуляции 50 px?**
A: Это компромисс: центры bbox в разных видах соответствуют разным точкам
грузовика. Меньше порог — больше отбраковки и дыр; больше — больше плохих точек.
Свип и обоснование — `experiments/geometry_sweep.py`, `docs/RESULTS.md` §5–8f.

**Q: Что делает Калман?**
A: Состояние `[x,y,z,vx,vy,vz]`, модель постоянной скорости; предсказание на
кадрах без измерения, обновление по 3D-измерению; RTS-сглаживание — офлайн.

**Q: Зачем гейт 10σ?**
A: При 3σ трек постоянно пересоздавался: 486 треков на 780 точек, 48 % точек с
нулевой скоростью. При 10σ — **49 треков**, доля нулевых скоростей **5 %**,
MAE прогноза **5.35 → 4.05 м**, MAE измерений не меняется (2.03 м).
Оговорка: для нескольких объектов гейт надо пересматривать.

**Q: Почему `max_missing=3` офлайн и 5 в пульте?**
A: Офлайн — чтобы не тянуть прогноз в метрику; в пульте 5 — компромисс, чтобы
маркер не «уезжал» при короткой окклюзии. В видео дополнительно есть
достройка до 2–3 с с серым пунктиром.

## 3. Детектор и обучение

**Q: Какие модели и почему?**
A: `v1` — yolov8s (быстрая), `v2` — yolov8m (53 эпохи), `v4` — yolov8m с нуля
(60 эпох), `v4b` — fine-tune v4 (20 эпох). Ансамбль повышает recall/покрытие;
v4b — лучший баланс для live.

**Q: На чём обучали?**
A: Псевдо-разметка из GT + 3D-модели (`tools/make_pseudo_labels.py`); реальной
2D-разметки нет. Это честно указано в ограничениях: на другой сцене выигрыш
будет меньше.

**Q: Почему финальный MAE 1.98, а у v4 1.55?**
A: Разные цели. v4 точнее (1.55 м), но покрытие 78.5 % / holdout 53.8 %.
v1+v2+v4b даёт 82.3 % / holdout 67.4 % при MAE 1.98. Для задачи «покрытие 90 %»
выбран вариант с большим recall.

**Q: Почему ансамбль ухудшает MAE?**
A: Он добавляет истинные, но более «рыхлые» детекции: покрытие растёт, средняя
ошибка тоже. Это trade-off, а не ошибка.

**Q: Сколько времени обучали?**
A: v1 — 16.1 мин (16 эпох), v4 — 50.2 мин (60 эпох), v4b — 21.1 мин (20 эпох);
v2 — 53 эпохи. GPU — RX 7900 XT, ROCm-PyTorch.

**Q: Почему ROCm, а не CUDA?**
A: Карта AMD; ROCm-PyTorch нативно работает на Windows (проверено, `torch.cuda`
= True, matmul ≈780× быстрее CPU). Детали — `docs/RESULTS.md` §8h.

**Q: Почему не используете TTA?**
A: Проверяли: recall-прокси 0.624 → 0.642, но MAE 1.55 → 1.81, holdout 1.61 →
2.13. Как финал отвергнуто, оставлено опцией.

**Q: Почему не hard-negative v3?**
A: Обучение с негативами деградировало модель; рабочая конфигурация осталась
v1+v2 (подробности — §8d). Отрицательный результат зафиксирован.

## 4. Якоря и калибровка

**Q: Что такое якорь по наборам видов?**
A: Медианный 3D-сдвиг `(оценка − GT)` для каждого набора видимых камер,
применяется после триангуляции. Он компенсирует систематическое расхождение
«центр bbox ↔ пивот».

**Q: Насколько он помог?**
A: Без сдвига MAE 11.89 м; общий 3D-сдвиг 7.40; 2D по камерам 10.00; сдвиг по
наборам видов **4.28 м** (in-sample). Parity-CV и time-CV показывают перенос:
например, cam3|cam5 — 10.35 → 4.51 (parity) / 3.65 (time).

**Q: Это не подгонка под GT?**
A: Якоря действительно фитируются по GT, но:
* проверка на чётных/нечётных кадрах (parity-CV) и на 600..1000 (time-CV);
* holdout-числа приведены отдельно;
* для новой сцены якоря надо перекалибровать — это ограничение, не скрываем.
Финальная строка 1.98 м — in-sample по якорям; holdout 1.98 м / 67.4 %.

**Q: Что такое азимутальный якорь?**
A: Поправка рядом Фурье (2 гармоники) по углу `az = bearing(камера→объект) −
heading`:
`corr(az) = c0 + c1 cos az + s1 sin az + c2 cos 2az + s2 sin 2az`.
Курс берётся из соседних точек трека, не из GT; коэффициенты — ridge-регрессия
(без неё holdout «взрывался»).

**Q: Что он дал?**
A: На ансамбле v1+v2: MAE 2.02 → **1.48 м**, holdout 2.06 → **1.71 м**;
parity-CV 1.72 совпадает с holdout 1.71 — переносится во времени, не подгонка.

**Q: Почему не общий 3D-сдвиг?**
A: Один вектор не описывает разные виды; leave-one-camera-out даёт 32–119 px
остаточной невязки. Отвергнут.

**Q: Почему не 2D-сдвиг по камерам?**
A: На train улучшает, на holdout 14.17 м — хуже, чем без него; тоже отвергнут.

## 5. Метрики и результаты

**Q: Что такое MAE здесь?**
A: Средняя евклидова ошибка 3D-позиции против GT по точкам `MEASURED`, метры.
Медиана 1.42 м, P95 4.98 м, максимум 16.65 м (хвост).

**Q: Что такое покрытие?**
A: Доля кадров, где получено измерение (не прогноз): **82.3 %** = 824 кадра с
измерением / 1001. MAE при этом считается по **823** точкам, для которых есть
GT (один измеренный кадр без GT).

**Q: Почему holdout MAE такой же 1.98, а покрытие ниже 67.4 %?**
A: В конце клипа меньше видов (cam1/cam2 уходят), поэтому меньше измерений; на
тех кадрах, где измерение есть, точность сохраняется.

**Q: Что такое recall/precision-прокси?**
A: 2D-разметки нет. Recall-прокси — доля кадров, где проекция GT-пивота попала
в bbox; precision-прокси — доля детекций, в которых оказался пивот. Это прокси,
не классические метрики.

**Q: Финальные числа — это in-sample или честная оценка?**
A: MAE 1.98 — in-sample по якорям (якоря фитились по всему клипу). Честные
проверки: parity-CV 1.72 м и holdout 1.98 м / 67.4 %. Это указано в README и
RESULTS; не выдаём in-sample за перенос.

**Q: Какая относительная точность?**
A: Финальная медиана 1.42 м, P95 4.98 м, максимум 16.65 м. На дальности
100–200 м это порядка 1–5 % в зависимости от кадра. Точная метрология
невозможна: единицы мира не подтверждены, а «метр» датасета может быть не
физическим метром.

**Q: Что такое oracle 95.5 %?**
A: Боксы, построенные из GT + 3D-модели (идеальные по построению). Это верхняя
граница конвейера, **не реальный детектор**. 95.5 % / 1.29 м, holdout 85.7 % /
1.03 м. Показывает, что геометрия позволяет 90 %+, но нужен recall ~0.9.

## 6. Почему не 90 %, не 93 % и не 30 fps

**Q: Почему не достигли 90 % покрытия?**
A: Упирается в recall детектора: 0.62–0.676 при нужных ~0.9. Ослабление порогов
даёт 86.8 %, но MAE растёт до 2.86 м; oracle-потолок 95.5 %. Честно: 90 % не
достигнуто.

**Q: А 93 %?**
A: На **полном** клипе реально 82.3 %. 93.0 % есть только на фрагменте 0..213
(199/214 кадров), и это явно подписано; MAE на фрагменте 2.77 м. Выдавать
фрагмент за весь клип нельзя.

**Q: Почему на видео таблица показывает 82.3 %, а не 93 %?**
A: Потому что это фактические накопленные метрики. Отметку «цель 93 %» и её
маркер убрали по запросу; остались только факты.

**Q: Почему live-пульт показывает 81.7 % / 2.89 м, а офлайн 82.3 % / 1.98 м?**
A: Это разные прогоны. Live — одна v4b через пульт: 81.7 % / 2.89 м. Офлайн —
v4b: 81.7 % / **1.86 м**, ансамбль v1+v2+v4b: 82.3 % / **1.98 м**. Разница
live/офлайн по MAE — из-за онлайн-прогона и настроек (в частности, азимутальная
поправка в пульте применяется к последней точке трека); точную причину не
локализовали, поэтому не подменяем числа. Оба результата реальные.

**Q: Почему не 30 fps?**
A: 5 камер × YOLO на каждом кадре; v4b даёт 8.5–9.8 fps при 960 px и превью
0.5. 30 fps не держим. Пути ускорения: батчинг 5 кадров, меньше `imgsz`, ONNX,
меньше камер. Ансамбль в реальном времени не тянет.

**Q: Почему бы не использовать ансамбль в live?**
A: Три модели на 5 камер не влезают в бюджет времени; live выбрана v4b
(покрытие 81.7 % офлайн). Ансамбль остаётся для офлайн-метрик и видео.

**Q: Почему видео лучше пульта?**
A: Видео рендерится офлайн из финального ансамбля и всех кадров; пульт — live
одной моделью. Это ограничение железа/времени, не «подкрутка».

## 7. Пропуски, ошибки, отрицательные результаты

**Q: Почему на графике ошибки есть разрывы?**
A: Это кадры, где триангуляция не дала измерение. Детекции при этом могут быть:
например, 45..59 — 3 вида (cam1/cam2/cam5), но средняя невязка чуть выше 50 px;
на кадре 60 — 49.9 px, и измерение появляется. После 3 пропусков трек
сбрасывается. Второй крупный разрыв — 386..427 (12.9–14.2 с), та же причина.

**Q: Почему не поднять порог 50 px?**
A: Проверяли: при 80 px покрытие 90.4 %, но MAE 8.71 м — точки геометрически
неверные. Лучше честная дырка, чем красивая ложь. Документированный компромисс:
conf 0.10 / 200 px даёт 86.8 % при MAE 2.86 м.

**Q: Почему на 551..572 даже oracle даёт 6.39 м?**
A: Это не проблема боксов: там геометрия/видимость, поэтому обучение центра не
поможет. Важно не обещать «закроем все дыры».

**Q: Можно ли дообучить модель на пропусках?**
A: Пробовали корректор центра (ResNet18 + эмбеддинг камеры): ошибка центра на
val 93.7 → 17.7 px, но holdout 134.3 → 75.3 px; 3D-результат — MAE **5.21 м**
(с якорями) и 4.25 м (без), покрытие не выросло. Отвергнуто, код в ветке
`experiment/keypoint-gaps`. Это честный отрицательный результат.

**Q: Что ещё отвергнуто?**
A: общий 3D-сдвиг, 2D-сдвиг по камерам, hard-negative v3, покадровое уточнение
меток, TTA, корректор центра. Всё зафиксировано в `docs/RESULTS.md` §8.

**Q: Что самое слабое место проекта?**
A: recall детектора 0.62–0.676; расхождение «центр bbox ↔ пивот»; единицы мира
и PTS не подтверждены; один клип. Мы это не скрываем и показываем, где потолок.

## 8. Веб-пульт, видео, GT

**Q: Что умеет пульт?**
A: 5 MJPEG-камер + план X–Y, пауза, `conf ±`, кнопка «Эталон» (GT), JSON
`/api/stats`; путь со сглаживанием SG, прогноз, серые пунктиры разрывов; таблица
прогона через `pecstorm dashboard-report`.

**Q: Что показывает кнопка «Эталон»?**
A: Жёлтую линию GT на плане и жёлтый крест GT на камерах. Она **не влияет** на
трекинг и метрики; это визуальный контроль.

**Q: Какая модель в пульте?**
A: v4b (`scene_v4b_ft/weights/best.pt`) + её якоря/азимут; `max_missing=5`,
`bridge=2 с`. Запасной быстрый вариант — v1 (10.5–12 fps), но покрытие ниже.

**Q: Почему путь на видео/карте сглажен?**
A: Фильтр Савицкого–Голея по ±5 точкам, края продолжаются линейно; разрывы
данных — серый пунктир, скачки >10 м рвут линию. Это визуализация, не меняет
метрики.

**Q: Что за белый пунктир?**
A: Прогноз вперёд по средней скорости последнего непрерывного участка
измерений на 3 с. Это экстраполяция, не измерение.

**Q: Где видео?**
A: `out/truck/videos/` (в git не входят): 5 камер + `map_plan.mp4`,
`dashboard_gt.mp4` (полный, 82.3 % / 1.98 м), `dashboard_93_fragment.mp4`
(фрагмент 0..213, 93.0 % / 2.77 м).

**Q: Как сделать видео/таблицу?**
A: `pecstorm video`, `pecstorm dashboard-video`, `pecstorm coords-table`,
`pecstorm dashboard-report`, `pecstorm plot-gt`.

## 9. Честность и ограничения

**Q: Вы используете GT — это не читерство?**
A: GT используется для (а) обучения псевдо-разметки, (б) офлайн-калибровки
якорей, (в) оценки и (г) кнопки «Эталон». В рантайме трекинг GT не читает.
Калибровка на GT всего клипа — ограничение; поэтому есть parity-CV/holdout и
оговорка, что для новой сцены якоря надо перекалибровать.

**Q: Единицы мира — метры?**
A: Не подтверждено. Подгонка 3D-модели даёт масштаб ≈3.06, то есть «метр»
датасета может быть не физическим метром. Вопрос организаторам №4/5.

**Q: Синхронность камер по PTS?**
A: Не подтверждена; используем номер кадра и 30 fps. Вопрос №6. При рассинхроне
50 мс и 2.5 м/с синтетика даёт ~0.12 м — но это синтетика, не гарантия.

**Q: Что будет на скрытом наборе?**
A: Числа будут хуже: другая сцена, другие камеры, нет GT для якорей. Пайплайн
переносим, но якоря и пороги надо калибровать; обещать 1.98 м нельзя.

**Q: 90 % покрытия — требование?**
A: В ТЗ численного target нет (вопрос №10). 90 % — наша внутренняя цель; мы
честно говорим, что 82.3 % и почему.

**Q: Почему не используете sidecar-репары GT?**
A: Они `verified_by_organizer=false`; по умолчанию не применяются, чтобы не
подгонять оценку. Кадры 402/691 просто исключены.

**Q: Как убедиться, что числа не выдуманы?**
A: Они воспроизводятся командами и лежат в артефактах: `results/truck/`,
`out/truck/eval_final/`, `out/truck/eval_center*`; в `results/` есть JSON/CSV,
графики и таблицы. Тесты — 90; историю прогонов можно пересчитать
`pecstorm`-командами. Мы специально фиксируем и отрицательные результаты.

**Q: Почему видео не в git?**
A: 5 MP4 + dashboard-запись — сотни мегабайт; `out/` в `.gitignore`. В

## 10. Каверзные вопросы

**Q: Ваш MAE 1.98 м — это много?**
A: На дальности 100–200 м это ~1–2 %; медиана 1.42 м. Для сравнения: база COCO
4.28 м, oracle 1.29 м. Для «попасть в грузовик» — нормально; для сантиметров
нужна 3D-модель/кейпоинты.

**Q: Почему не измеряете скорость/ускорение?**
A: Калман оценивает скорость, но GT для неё нет; метрика — позиция. Прогноз
оценивается отдельно (MAE прогноза 8.02 м на 22 точках), это не точность
измерения.

**Q: Почему на графике ошибка в X больше, чем в Y/Z?**
A: Геометрия сцены и базовые линии камер: X хуже наблюдается. По осям MAE:
X 1.54, Y 0.89, Z 0.35 м. Якоря и азимут уменьшают, но не убирают.

**Q: Что если детектор ошибся?**
A: Триангуляция/гейт отбрасывают несогласованные кандидаты; при пропуске —
прогноз/дырка. Ложные срабатывания low-score видны в пульте, поэтому conf 0.25
и фильтр по score ≥0.5 в обучении корректора.

**Q: Почему 3D-точка Z ≈ 3 м?**
A: Пивот грузовика на высоте ~3 м в мировых координатах; Z — высота. Траектория
в плане — X/Y.

**Q: Как проверяли, что не переобучились?**
A: parity-CV (чётные/нечётные), holdout 700..1000, time-CV для якорей, отдельные
прогоны v1/v2/v4/v4b. Ограничение: один клип; hidden set не проверяли.

**Q: Что бы сделали за ещё месяц?**
A: keypoint/pivot-модель вместо центра bbox; recall до ~0.9; батчинг/ONNX для
fps; проверка единиц/PTS с организаторами; мульти-объект; 3D-модель на рантайме.
